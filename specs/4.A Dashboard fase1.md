# Plan — Dashboard INTEGRA, Fase 1: Arquitectura de Lectura (Ledger → Dashboard)

## Contexto y prioridad

Este es el primer paso de un nuevo frente: un dashboard visual que muestre lo que INTEGRA (el backend real, en `INTEGRAlab`) ya logra. Nos inspiramos en la UX/producto de un proyecto de una compañera (`INTEGRA-MVP`, 100% simulado — blockchain en memoria del navegador, PKI decorativa, DB vacía), pero **la arquitectura, el ledger, la PKI, el endorsement y los 18 tests de seguridad de INTEGRAlab son la fuente de verdad y NO se modifican, no se reemplazan ni se simplifican para "parecerse" al otro proyecto.** Este dashboard es una capa nueva que se apoya en lo que ya existe; no toca `nodes/`, `certs/` (generación), ni la lógica de endorsement/PKI ya validada por la suite de tests.

**Regla dura para esta fase:** ningún cambio en esta spec debe requerir modificar `server.js`, la lógica de chaincode/endorsement, ni los tests existentes. Si en algún punto parece necesario, DETENERSE y avisar antes de tocar nada de eso — mismo criterio que la regla de checkpoint que usamos para la suite de seguridad.

## Decisión de arquitectura: Ledger + capa de proyección (no reemplazo por base de datos)

Ya está resuelto conceptualmente en `docs/INTEGRA_Paso2_Arquitectura.docx` (datos on-chain/off-chain, canales privados) y `docs/INTEGRA_Paso3_Implementacion.docx` (Tabla 4, respuesta a Ley 25326). Esta fase lo hace concreto en código:

- **El ledger (tal como está) sigue siendo la única fuente de verdad** para: registro de donante, endorsement de lista de espera, asignación, y checkpoints de cadena de custodia. No se toca su lógica de escritura ni de validación.
- **Se agrega una capa de LECTURA/proyección** — no una base de datos relacional nueva, no MySQL, no Prisma. Es un módulo que lee el ledger existente (via los endpoints de consulta que ya tengan los nodos, o leyendo `data/*/ledger.json` si no hay endpoint de lectura aún) y lo transforma a una forma que un dashboard puede consumir directo: timeline de eventos ordenado, estado actual de un caso, historial de temperatura de custody, resumen de firmas.
- Esta capa es **derivada, no autoritativa**: si alguna vez hay una discrepancia entre lo que muestra el dashboard y lo que dice el ledger, el ledger tiene razón. El dashboard nunca escribe directamente ahí — cualquier acción del dashboard (firmar, registrar) pasa por los endpoints reales existentes (`/sign`, `/tx`, etc.), igual que ya lo validan los tests.
- Telemetría de alta frecuencia (cada 90s o el intervalo que uses) puede vivir en esta capa de proyección para graficar (ej. `recharts`, que sí es una librería razonable a tomar prestada de la spec de tu compañera) sin necesidad de que cada lectura individual sea una transacción firmada nueva en el ledger — eso ya debería estar resuelto por cómo diseñaste `CustodyChain`, solo hay que confirmar cómo se consulta el histórico.

## Qué construir en esta fase (backend, sin UI todavía)

Un módulo nuevo, separado de la lógica de nodos existente, ej. `dashboard-api/` o `nodes/lib/dashboard-projection.js` (decisión de Claude Code según cómo esté organizado el repo hoy):

1. **`GET /dashboard/casos/:id`** — devuelve un JSON consolidado de un caso: estado del donante, estado de la lista de espera/asignación, resumen de custodia (última temperatura conocida, alertas activas), y quién firmó qué. Arma esto leyendo el ledger existente, no agrega estado nuevo.
2. **`GET /dashboard/casos/:id/timeline`** — lista ordenada de eventos (tipo, actor, timestamp, hash, firma válida sí/no) lista para renderizar en un feed tipo el `traceability.tsx` que vimos en la spec de referencia — pero con datos reales, no simulados.
3. **`GET /dashboard/casos/:id/telemetria`** — serie temporal de lecturas de custody (temperatura, timestamp) para alimentar un gráfico. Si hoy cada lectura ya es una transacción en el ledger, este endpoint simplemente las filtra y ordena; no se inventa una fuente de datos nueva.
4. **`GET /dashboard/health`** — estado de los 4 nodos (arriba/abajo, últimas transacciones), reusa lo que ya usa `npm run test:seguridad` para el health check.

Ningún endpoint nuevo debe tener lógica de autorización más débil que la que ya existe — si son de solo lectura para el dashboard, igual deben respetar el modelo de acceso (ej. un actor no debería poder consultar `/dashboard/casos/:id` de un caso fuera de su alcance si el diseño de canales privados ya restringe eso a nivel ledger).

## Qué NO construir en esta fase

- Nada de frontend/React todavía — eso es Fase 2.
- Nada de simulación de tiempo acelerado, roles ficticios, ni barra de control — eso es Fase 4, y ahí se decide qué se simula genuinamente (por honestidad, igual que hizo tu compañera con su tabla) vs. qué dispara acciones reales.
- Nada de base de datos relacional nueva. Si en algún momento el volumen de datos históricos (muchos casos, mucha telemetría acumulada) hace que leer el ledger completo en cada consulta sea lento, ahí se evalúa un caché/índice liviano (ej. SQLite local) — pero eso es una optimización de rendimiento futura, no una fuente de verdad nueva, y requiere aprobación explícita antes de implementarse.
- Nada de modelo de IA todavía — eso puede ser una fase separada (Fase 5), y ahí también aplica la misma honestidad: si no hay un modelo real entrenado, se declara explícitamente como no implementado en vez de simularlo como si lo fuera.
